# Spec: Song library and practice journal (v1)

## Problem Statement

I play guitar, piano and bass, and I have no system for any of it. I can't see which Songs I've learned on which Instrument, I have nowhere to write down how a Part is going, nothing tells me which Parts I'm about to forget or have neglected, and my links to tabs and tutorials are scattered across browser tabs and notes. I also have recordings of myself playing in Voice Memos that aren't connected to anything.

## Solution

A minimal, warm, "paper" style app that is my Library of Songs and the Parts I play on each Instrument. Each Part has a Status (Want to learn, Learning or Learned), a Part Note and Recordings. I log Practice Sessions, made up of Practice Entries, each with a one-tap Rating. A spaced-repetition scheduler (FSRS) uses those Ratings to decide when each Part is next Due, and **Practice Next** shows me what to practise today. Everything syncs through iCloud across iPhone, iPad and Mac, at no running cost.

This spec covers the first version. The data model is built for Shared Spaces (live sharing with bandmates and teachers), but the first version has no sharing interface.

Read `GLOSSARY.md` for the language used here, and ADR 0001 and ADR 0002 for the persistence and sharing decisions.

## User Stories

All stories are from the Musician's point of view.

### Library and Songs

1. Add a Song by typing its title and artist, so that I can start tracking it quickly.
2. Optionally record a Song's key, so that I remember what key I play it in.
3. Optionally record a Song's tempo in BPM, so that I can practise at the right speed.
4. Edit a Song's title, artist, key and tempo, so that I can fix mistakes.
5. See all Songs in my Library, so that I have one place for everything I play.
6. Search my Library by title or artist, so that I can find a Song quickly.
7. Delete a Song, after confirming, together with its Parts, Recordings and Resources, so that my Library stays clean.
8. A deleted Song disappears from every Collection it was in, so that Collections never show missing Songs.

### Resources

9. Attach Resources (links to tabs or tutorial videos) to a Song, so that my learning material lives with the Song.
10. Give a Resource an optional title, so that I can tell "UG tab" apart from "Marty Music lesson".
11. Open a Resource from the Song, so that I can get to the tab or video in one tap.
12. Edit and delete Resources, so that dead links don't pile up.

### Instruments

13. Create my own Instruments by name, so that the app fits whatever I play.
14. Instruments I've created before are offered when I add a Part, so that I don't retype them.
15. Rename an Instrument, so that I can refine names (for example "Guitar" to "Acoustic Guitar").
16. Be stopped from deleting an Instrument that Parts still use, so that I never lose Parts by accident.
17. Delete an Instrument that no Parts use, so that the list stays tidy.

### Parts

18. Add a Part to a Song for an Instrument, so that I track my progress on that Instrument separately.
19. Have Parts on several Instruments for the same Song, so that "Learned on guitar, Learning on piano" can both be true.
20. Give a Part an optional label (such as "Lead" or "Drop D"), so that I can track two Parts on the same Instrument.
21. Set a Part's Status to Want to learn, Learning or Learned, so that I know where I stand.
22. Move a Part's Status in any direction, so that I can move a Learned Part back to Learning when I've lost it.
23. A Part becomes Due right away when it first moves to Learning, so that I start practising it.
24. A Part's schedule carries over when I move it between Learning and Learned, so that changing Status doesn't throw away its history.
25. Want to learn Parts are never Due, so that my wishlist doesn't clutter Practice Next.
26. A single Part Note on each Part that I can keep editing, so that chord shapes and reminders stay in one place.
27. See all Parts with a given Status (for example all Want to learn), so that I can choose what to start next.
28. Filter Parts by Instrument, so that I can focus on piano today.
29. Delete a Part, after confirming, together with its Recordings and Practice Entries, so that removing it is complete.

### Collections

30. Create a named Collection, so that I can group Songs (for example "Friday Gig").
31. Add Songs to a Collection, so that it holds the Songs I need.
32. Reorder Songs in a Collection, so that it can act as a setlist.
33. Have a Song in several Collections, so that a Song can be in both "Friday Gig" and "Acoustic Set".
34. Remove a Song from a Collection without deleting the Song, so that Collections are easy to edit.
35. Rename and delete Collections, so that I can keep them current.
36. A Collection shows my Parts for each Song, so that I can see how ready I am for a gig.

### Practice Sessions and Practice Entries

37. Start a timed Practice Session, so that its duration is recorded automatically.
38. Log a Practice Session after the fact, entering its date and duration, so that I don't need a timer running.
39. Log several Practice Sessions on the same day, so that morning and evening practice are kept separate.
40. Add an optional note to a Practice Session, so that I can record context like "tired, fingers sore".
41. Add Practice Entries for Parts on different Instruments in one Practice Session, so that a mixed session is logged accurately.
42. Rate each Practice Entry Again, Hard, Good or Easy with one tap, so that logging is quick.
43. Add an optional written note to a Practice Entry, so that I can record how that Part went.
44. Attach a Recording to a Practice Entry, so that I can hear how I played on that day.
45. See a Part's practice history (dated Practice Entries with their Ratings and notes), so that I can see how I've improved.
46. See my past Practice Sessions, so that I can review how much I've been practising.
47. Edit or delete a Practice Session or Practice Entry, so that I can fix mistakes.
48. A Practice Session left with no Practice Entries is deleted automatically, so that empty sessions don't build up.
49. A logged Rating changes when the Part is next Due, so that hard Parts come back sooner and easy ones later.
50. Editing or deleting a Practice Entry recomputes its Part's schedule, so that the schedule always reflects my real history.

### Practice Next

51. A Practice Next list shows my Due Parts, so that I know what to practise today.
52. Practice Next is ordered most overdue first, so that the Parts I'm closest to forgetting come first.
53. Practice Next includes both Learning and Learned Parts, so that I keep up new Parts and old ones.
54. Start a Practice Session from Practice Next, so that going from "what's due" to practising takes one step.
55. A Part leaves Practice Next once I've logged a Practice Entry for it, so that the list shrinks as I work through it.

### Recordings

56. Record audio of myself playing a Part from inside the app, so that I capture my progress.
57. Import existing audio files (for example from Voice Memos or Files) as Recordings of a Part, so that old recordings join their Part.
58. Each Recording is dated, so that I can hear how I've progressed over time.
59. Play back a Part's Recordings, so that I can review my playing.
60. Delete a Recording, after confirming, so that I can discard bad takes.
61. Recordings stay on the Part even if the Practice Entry they were made in is deleted, so that I don't lose audio.

### Sync and platforms

62. My Library syncs through iCloud across my iPhone, iPad and Mac, so that I can practise with whichever device is nearby.
63. The app works offline and syncs later, so that practice logging never depends on a connection.
64. Recordings sync too, so that a take recorded on my phone plays back on my Mac.

### Look and feel

65. A warm, minimal "paper" look with no clutter, so that the app feels calm to use while practising.
66. Dark mode looks like dark paper with cream ink, so that practising at night doesn't feel jarring.
67. The iPhone layout is the primary design, so that it works on a music stand or in one hand.

## Screen Map

Top-level destinations: **Practice Next**, **Library** (Songs), **Parts** (filtered by Status and Instrument; Instruments are managed from here), **Collections** and **Practice Sessions**. Song, Part, Collection and Practice Session detail screens are reached from these.

- **macOS:** a sidebar of the top-level destinations on the left. Toggles hide the sidebar and any secondary panes, so the window can show one thing with minimal clutter whenever possible. Designed for full-screen windows.
- **iOS:** Spotify-style. One screen in focus at a time, each pushed full screen, with navigation arrows in the top corners (back top-left, the screen's main action top-right). Top-level destinations are switched with a bottom tab bar, as in Spotify.
- **iPad:** follows the macOS layout.

## Implementation Decisions

- **Persistence (ADR 0001):** Core Data with `NSPersistentCloudKitContainer`, using the private CloudKit database. The container is set up so a shared store can be added later without a schema change. Every attribute is optional or has a default, there are no unique constraints, relationships are optional, and there are **no ordered relationships** (CloudKit doesn't support them). Once the schema is deployed to production it can only gain fields, so ship only the fields listed here.
- **Model built in code:** the Core Data model is defined programmatically in MuseManCore, not in an `.xcdatamodeld` file, so that `swift test` can load it.
- **Sharing-ready model (ADR 0002):** Songs, Collections and Instruments each live in exactly one Library or Shared Space. The Library is the private store, not an entity. Practice Sessions and Practice Entries are never shared. A Practice Entry refers to its Part and its Recording **by identifier, not by a Core Data relationship**, so that sharing a Part never pulls in practice history; code following those identifiers must cope with the Part or Recording being missing.
- **Entities and fields:**
  - Song: title, artist, key (optional, free text), tempo in BPM (optional); has Resources, Parts and Collection Items.
  - Resource: URL, optional title; belongs to a Song.
  - Instrument: name; lives in one Library or Shared Space. A Part's Instrument is always in the same place as its Song. When a Song later moves into a Shared Space, its Parts' Instruments are matched by name in that Space, or created there.
  - Part: Song, Instrument, owner, optional label, Status, Part Note, due date (optional); has Recordings.
  - Collection: name; has Collection Items.
  - Collection Item: Collection, Song, position. This is how a Collection orders its Songs and how a Song belongs to many Collections.
  - Practice Session: start date, duration, optional note; has Practice Entries.
  - Practice Entry: Part identifier, Rating, optional note, optional Recording identifier, date.
  - Recording: date, audio data stored externally (so it syncs as a CloudKit asset); belongs to a Part.
- **Musician:** there is no Musician entity. A Part's owner is a CloudKit user record name string; in the first version it is left empty, meaning the current iCloud user. It exists so that Shared Spaces can show other Musicians' Parts later.
- **Deletion rules:**
  - Deleting a Song deletes its Parts, Resources, their Recordings and its Collection Items.
  - Deleting a Part deletes its Recordings and the Practice Entries that reference it.
  - A Practice Session left with no Practice Entries is deleted.
  - Deleting a Practice Entry keeps its Recording, because Recordings belong to the Part.
  - An Instrument can only be deleted when no Part uses it.
- **Status and scheduling:**
  - Scheduling works in **whole days**. A Part's due date is a calendar day, and every interval is at least one day, including after Again.
  - Only Learning and Learned Parts are scheduled. Want to learn Parts are never Due, whatever their due date.
  - When a Part moves to Learning and has no due date, its due date becomes today. A Part that already has a due date keeps it, so moving between Learning and Learned, or out to Want to learn and back, keeps its schedule.
  - A Part is Due when its due date is today or earlier.
  - Practice Next lists Due Parts, earliest due date first.
  - Several Practice Entries for the same Part on the same day count as one review, using the last Rating.
  - If every Practice Entry for a Part is deleted, its due date becomes today.
- **FSRS scheduler:** a local FSRS (FSRS-5, default parameters) implementation inside MuseManCore, with **no third-party dependency**. It is an internal detail behind `PracticeLibrary`. Only the due date is stored. FSRS state (stability, difficulty) is recomputed from the Part's Practice Entries' Ratings each time, which makes editing or deleting a Practice Entry safe and allows parameter tuning later.
- **`PracticeLibrary` (the one seam):** an `@Observable`-friendly interface in MuseManCore covering everything the first version does: Songs, Resources, Instruments, Parts, Collections, Practice Sessions, Practice Entries, Recordings, and the Practice Next query. It is built with two things passed in from outside: the persistent store (CloudKit-backed in the app, in-memory in tests) and the current date. The CLAUDE.md `@Observable` rule has an exception for `NSManagedObject`, but views should depend on `PracticeLibrary` and plain value types where practical.
- **Recordings:** record in the app with AVFoundation, and import through SwiftUI's file importer. Audio data uses external storage.
- **App target:** one multiplatform SwiftUI target (iOS and macOS), with iPhone as the primary design. Xcode changes for the developer to make: add the macOS destination, turn on the iCloud (CloudKit) and Background Modes (remote notifications) capabilities, add a microphone usage description, and bundle the DM Sans and DM Serif Display font files (OFL).
- **Zero running cost:** CloudKit's private database only, with no server, so the app can ship publicly without a subscription.
- **Design tokens:**
  - Colours: warm off-white paper background; ink text; teal accent in light mode; soft orange-red accent in dark mode; dark-paper background with cream ink in dark mode.
  - Fonts: DM Serif Display for titles, DM Sans for body text, so that the app reads like a well-set notebook.
  - Surfaces: hairline separators, no shadows, no cards.
  - Anything irreplaceable (Recordings, practice history) asks for confirmation before it is deleted.

## Testing Decisions

- A good test drives `PracticeLibrary` through its public interface and checks what a user would observe: what's in the Library, a Part's Status, Practice Next contents and order, and what remains after a deletion. Tests don't touch Core Data objects, the FSRS internals, or private state.
- **One seam:** `PracticeLibrary` with an in-memory store and a controllable clock. FSRS is tested through it, for example: "rate a Part Easy, move the clock forward a day, the Part isn't in Practice Next; move it forward far enough, it is".
- Behaviour to cover:
  - Adding and editing Songs, Parts, Resources, Instruments and Collections.
  - Collection ordering and a Song belonging to several Collections.
  - Status transitions, including becoming Due when first entering Learning, and the schedule being kept between Learning and Learned.
  - Want to learn Parts never being Due.
  - Practice Next order (most overdue first) and Ratings changing when a Part is next Due.
  - A Part rated Again not returning to Practice Next until the next day.
  - Several Practice Entries for the same Part on the same day counting as one review.
  - Editing or deleting a Practice Entry recomputing the schedule.
  - All the deletion rules, including Practice Sessions removed when empty and Recordings outliving their Practice Entry.
  - Instrument deletion being blocked while Parts use it.
  - Several Practice Sessions on the same day.
- Not tested: SwiftUI views, CloudKit sync, audio capture.
- Prior art: the Swift Testing tests in the MuseManCore test target (for example `GreetingTests`), which use `@Test` and `#expect` against the public API. Run with `swift test --package-path Packages/MuseManCore`.

## Out of Scope

- Any sharing interface (Shared Spaces, invitations, permissions, leaving a Space). The model supports it per ADR 0002, but there is no UI in the first version.
- Notifications and reminders.
- Exercises (scales, technique drills, warm-ups).
- Video Recordings.
- File attachments on Resources (PDFs, images); links only.
- Apple Music / MusicKit search and album artwork; Songs are entered by hand.
- Instrument-specific Part fields (tuning, capo).
- Tuning FSRS parameters to a Musician's history.
- Merging duplicate Songs or Instruments.
- Choosing the app's name.

## Further Notes

- "Muse-man" is a working name.
- Recordings can't be replaced, so deleting anything that contains them must ask for confirmation.
- Before the first public release, double-check the CloudKit production schema: fields can't be removed afterwards.
